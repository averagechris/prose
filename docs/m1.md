# M1 reference

M1 is deterministic, model-free infrastructure. It stores and serves material
supplied by the user; it never judges content, calls a model, invents a verb,
or approves on someone's behalf. Names in examples are ordinary user content,
not built-ins. The binary ships no packs, modules, verbs, mappings, or tiers.
`packs/starter.json` is a separate data artifact that must be imported
explicitly. It supplies four generic operation documents and intentionally
contains no code-review voice module.

## Store and schema v1

The database is `$XDG_DATA_HOME/prose/prose.db`, or
`$HOME/.local/share/prose/prose.db`; `--store` overrides `PROSE_STORE`, which
overrides that default. prose creates directories as `0700` and the database
and SQLite WAL/SHM files as `0600` on Unix. Symbolic and multiply hard-linked
database files are rejected. Existing override directories are not chmodded.
Connections use foreign keys, a five-second busy timeout, and WAL. Concurrent
writers serialize; expected revisions make competing logical updates fail as
stale rather than branch.

Schema version 1 is defined directly (there is no prior shipped schema). Every
table is SQLite `STRICT`:

- `packs(id)` owns immutable pack IDs.
- `setting_events(sequence, key, value_json, created_at)` is the append-only
  settings log. M1 uses `active_pack`; import does not select it unless asked.
- `pack_revisions(pack_id, revision, description, tombstone, created_at)` is
  the append-only pack header/tombstone log.
- `context_revisions(pack_id, pack_revision, name, description, content)`
  stores context snapshots.
- `verb_revisions(pack_id, pack_revision, name, description, family,
  instructions, length_unit, length_min, length_max, no_new_claims,
  preserve_meaning)` stores typed verb snapshots.
- `verb_context_binding_revisions(pack_id, pack_revision, verb_name,
  context_name)` stores category-checked verb-to-context references.
- `audience_tier_revisions(pack_id, pack_revision, name, description,
  requirements_json)` stores tiers.
- `surface_mapping_revisions(pack_id, pack_revision, surface, context_name,
  default_audience_tier)` maps each surface to same-revision content.
- `drafts(id, context_pack_id, context_pack_revision, context_name,
  verb_pack_id, verb_pack_revision, verb_name, created_at)` freezes exact pack
  revisions at draft creation. `draft_versions(draft_id, version,
  parent_version, content, author_kind, provenance_json, created_at)` is a
  non-branching append-only chain and records whether each version came from a
  human, agent, capture, or import operation.
- `attestation_batches(sequence, id, human_approved, approved_by, via_harness, via_session,
  method, tier_pack_id, tier_pack_revision, tier_name, created_at)` is the
  bulk-first approval event. `attestations(id, batch_id, draft_id,
  draft_version, decision, exceptions_json)` stores each exact approved or
  excepted item and its exceptions.

Composite foreign keys enforce every context, verb, tier, draft-version, and
pack-revision reference. Triggers reject updates/deletes to immutable and
append-only data, enforce string-only JSON arrays, and close each attestation
batch against later members when its batch row is inserted. Initialization is
transactional and verifies the application ID, strict tables, exact column
sets, required schema objects, and foreign-key integrity on reopen.

## Strict pack JSON

All input objects reject unknown fields and trailing JSON. Closed choices are
enums, not free-form strings. Keys are 1–128 ASCII letters, digits, `.`, `_`,
or `-`; collections reject duplicate keys. References are validated
deterministically before storage. Lists that are semantic sets are returned in
stable key order.

```json
{
  "id": "personal",
  "description": "My authoring material",
  "contexts": [{
    "name": "reviews",
    "description": "How I communicate review findings",
    "content": "State actionable evidence directly."
  }],
  "verbs": [
    {
      "name": "tighten",
      "description": "My tightening operation",
      "family": "transform-selection",
      "instructions": "Remove repetition without changing meaning.",
      "context_bindings": ["reviews"],
      "constraints": {
        "length": {"unit": "words", "min": 5, "max": 100},
        "no_new_claims": true,
        "preserve_meaning": true
      }
    },
    {
      "name": "draft",
      "description": "Turn stated intent into a draft",
      "family": "draft-from-intent",
      "instructions": "Express only the supplied intent.",
      "context_bindings": ["reviews"],
      "constraints": {
        "length": null,
        "no_new_claims": true,
        "preserve_meaning": true
      }
    }
  ],
  "audience_tiers": [{
    "name": "team",
    "description": "Colleagues",
    "requirements": ["I reviewed the exact final draft"]
  }],
  "surface_mappings": [{
    "surface": "github-pr",
    "context": "reviews",
    "default_audience_tier": "team"
  }]
}
```

`family` is exactly `transform-selection` or `draft-from-intent`. `length` is
`null` or an object whose `unit` is `characters` or `words`, with at least one
positive `min`/`max` and `min <= max`. `no_new_claims` and
`preserve_meaning` are instructions served to an attached agent; prose records
them but never judges compliance. Every context binding and surface mapping
must resolve inside the same complete pack revision.

Commands include `pack create`, `pack update --expected-revision N`, `pack get
ID [--revision N]`, `pack list`, `pack delete ID --expected-revision N`,
`pack import`, `pack export`, `pack item put|delete`, and `pack use ID`.
`context NAME`, `verb NAME`, `verbs`, and `surface NAME` use the explicitly
selected pack unless `--pack ID` is supplied. They serve exact revisions and
never choose material semantically.

## Drafts and frozen provenance

`draft create` accepts user content and optional active context/verb refs:

```json
{
  "id": "review-42",
  "content": "Initial text",
  "context": {"pack_id": "personal", "name": "reviews"},
  "verb": {"pack_id": "personal", "name": "tighten"},
  "author_kind": "agent",
  "provenance": {"session": "example"}
}
```

The response replaces each supplied name-only reference with frozen provenance:

```json
{
  "draft_id": "review-42",
  "version": 1,
  "parent_version": null,
  "content": "Initial text",
  "context": {"pack_id": "personal", "pack_revision": 1, "name": "reviews"},
  "verb": {"pack_id": "personal", "pack_revision": 1, "name": "tighten"},
  "created_at": "..."
}
```

Later pack updates cannot change this provenance. `draft revise ID
--expected-version N --content FILE` appends exactly to the current head;
`draft get ID [--version N]` retrieves the head or an exact old version.

## Bulk human approval attestations

One `attestation record` input is one atomic, bulk-first event:

```json
{
  "human_approved": true,
  "approved_by": "Chris",
  "via": {"harness": "opencode", "session": "session-42"},
  "method": "verbal-lgtm",
  "audience_tier": {"pack_id": "personal", "name": "team"},
  "items": [
    {"draft_id": "review-42", "version": 2, "decision": "approved", "exceptions": []},
    {"draft_id": "announcement", "version": 1,
     "decision": "excepted", "exceptions": ["Use the shorter title"]}
  ]
}
```

Each item has `"decision": "approved"` or `"excepted"`; omitted decisions
default to approved for compatibility. Excepted items require a non-empty
reason, and every batch needs at least one approved item. `method` is exactly
`verbal-lgtm` or `explicit`. Harness and session are both
required. `human_approved` must literally be true: it is the caller's explicit
assertion that the named human approved these exact versions. Items must be
non-empty and unique, exceptions must contain non-empty text, the audience tier
revision is frozen, and any invalid item rolls back the entire event. prose
trusts the harness report; it never infers or supplies approval.

`attestation list [--draft ID]` returns deterministic event/item order and
round-trips approver, harness/session, method, frozen tier revision, exact draft
version, per-item exceptions, batch ID, and timestamp.

## Output and errors

With `--json`, commands emit one compact JSON document: successes to stdout
and failures to stderr. Mutations use `{"action":"...","item":...}`, lists
use `{"items":[...]}`, and show/serve commands return the resource directly.
Without `--json`, output is human-readable pretty JSON and errors are plain
text.
Stable error codes are `usage_error`, `invalid_input`, `not_found`,
`stale_revision`, `conflict`, `io_error`, and `storage_error`. Missing draft
heads and versions are explicitly identified as drafts. `--help` and
`--version` are the conventional human-readable exceptions.
